# Probar T-06: API y PostgreSQL con Docker Compose

Esta guía verifica la construcción de la API, su conexión con PostgreSQL, autenticación y consultas reales, ejecución sin privilegios y el volumen de archivos. Usa `docker-compose.yml` en la raíz del repositorio.

El alcance de esta entrega es API y base de datos. La contenedorización del frontend que requiere el plan actual de Fase 4 queda pendiente en una entrega separada.

Los comandos corresponden a PowerShell. Docker Desktop debe estar iniciado y utilizar contenedores Linux. La compilación de .NET ocurre dentro de la imagen.

## 1. Preparar la configuración local

Desde la raíz del proyecto, crea `.env` si todavía no existe:

```powershell
cd C:\Proyectos\UPractice

if (-not (Test-Path -LiteralPath .env)) {
    Copy-Item -LiteralPath example.env -Destination .env
}
```

Abre `.env` en tu editor y completa valores propios:

| Variable | Uso |
|---|---|
| `POSTGRES_PASSWORD` | Contraseña de PostgreSQL y de la conexión de la API. |
| `SUPERADMIN_PASSWORD` | Contraseña inicial de `admin@upractice.app`. |
| `DEMO_PASSWORD` | Contraseña inicial de las cuentas de demostración. |
| `API_PORT` | Puerto del equipo para la API; predeterminado `8080`. |
| `POSTGRES_PORT` | Puerto del equipo para PostgreSQL; predeterminado `5433`. |

Las tres contraseñas son obligatorias. Usa valores distintos de 8 a 64 caracteres, con mayúscula, minúscula y número. Para esta configuración evita `;`, comillas y `$` en las contraseñas.

`JWT_CLAVE_FIRMA` y `JWT_CLAVE_CIFRADO` pueden quedar ambas vacías en este entorno Development: la API genera claves temporales y se debe iniciar sesión de nuevo después de reiniciarla. Si deseas fijarlas, completa ambas con claves Base64 distintas, de 32 bytes cada una. El ejemplo de generación está en `example.env`.

`.env` queda en tu máquina, ignorado por Git. Las capturas y el PR deben omitir contraseñas, tokens y cabeceras Authorization. Usa `config --quiet`: la salida completa de `docker compose config` contiene los valores interpolados.

## 2. Validar y levantar los servicios

```powershell
docker compose config --quiet
```

Si falta alguna contraseña, Compose muestra qué variable debes completar. Continúa cuando termine correctamente:

```powershell
docker compose up -d --build --wait
docker compose ps
```

La primera construcción descarga las imágenes y restaura los paquetes. `db` debe estar saludable antes del arranque de `api`; `--wait` comprueba que los servicios queden listos.

Con los puertos predeterminados:

- Swagger: `http://localhost:8080/swagger`.
- Comprobación HTTP: `http://localhost:8080/health`, respuesta esperada `{"estado":"ok"}`.
- PostgreSQL desde el equipo: `127.0.0.1:5433`.
- PostgreSQL desde la API: nombre de servicio `db`, puerto interno `5432`.

Si cambiaste `API_PORT` o `POSTGRES_PORT`, utiliza esos valores al abrir el navegador o conectar DBeaver. El PostgreSQL manual `upractice-pg` en `5432` usa otro contenedor y otro almacenamiento.

Para revisar el arranque:

```powershell
docker compose logs --tail=80 api
```

El arranque aplica migraciones y carga el seed según la configuración. `/health` es una respuesta HTTP estática; las consultas de los siguientes pasos comprueban también el acceso real a la base de datos.

## 3. Consultar la base en DBeaver

Crea una conexión PostgreSQL:

| Campo | Valor predeterminado |
|---|---|
| Host | `127.0.0.1` |
| Puerto | `5433` |
| Base de datos | `upractice` |
| Usuario | `upractice` |
| Contraseña | Tu `POSTGRES_PASSWORD` de `.env`. |

Comprueba las tablas en el esquema `public`. Para obtener una vacante de la empresa del reclutador de demostración:

```sql
SELECT v."Id" AS "vacanteId", v."Titulo", e."NombreComercial"
FROM "Vacantes" v
JOIN "Empresas" e ON e."Id" = v."EmpresaId"
JOIN "Usuarios" u ON u."EmpresaId" = e."Id"
WHERE u."Correo" = 'rrhh@digitales.example.com'
ORDER BY v."Titulo";
```

Copia un `vacanteId` real. Para documentar después el reinicio de la base, guarda también el identificador del SuperAdmin:

```sql
SELECT "Id", "Correo"
FROM "Usuarios"
WHERE "Correo" = 'admin@upractice.app';
```

## 4. Probar autenticación y una consulta de negocio

En Swagger, ejecuta `POST /api/v1/auth/login`:

```json
{
  "correo": "rrhh@digitales.example.com",
  "password": "<tu DEMO_PASSWORD>"
}
```

Reemplaza el marcador por tu valor local. La respuesta esperada es 200, con el usuario, su empresa y `accessToken`. Copia solo el token y pégalo en **Authorize**.

1. Ejecuta `GET /api/v1/auth/me`: debe responder 200 con el reclutador autenticado.
2. Ejecuta `GET /api/v1/empresa/vacantes/{vacanteId}/postulaciones`, usando el ID obtenido en DBeaver: debe responder 200 con una lista de postulantes.
3. Pulsa **Logout** en Authorize y ejecuta `/api/v1/auth/me` sin token: debe responder 401.
4. Inicia sesión como `ana.lopez@unah.hn`, con `DEMO_PASSWORD`, y autoriza ese token. La consulta de postulantes de empresa debe responder 403 por rol.
5. Inicia sesión como `rrhh@finanzas.example.com`, con `DEMO_PASSWORD`, y consulta la vacante anterior: debe responder 404 porque pertenece a otra empresa.

El SuperAdmin es `admin@upractice.app` y utiliza `SUPERADMIN_PASSWORD`. Puede consultar `/auth/me` al ingresar. Su cuenta inicial exige cambiar la contraseña: las operaciones administrativas protegidas devuelven 403 `CAMBIO_PASSWORD_REQUERIDO` hasta completar `PUT /api/v1/auth/password` y autorizar el token nuevo.

Las contraseñas de los contenedores proceden de `.env`, no de los user-secrets del arranque local con `dotnet run`. Cambiar una contraseña del seed en `.env` no actualiza cuentas que ya existen en una base en ejecución.

## 5. Verificar el usuario y el volumen de archivos

```powershell
docker compose exec -T api id
docker compose exec -T api dotnet --list-sdks
docker compose exec -T api dotnet --list-runtimes
```

El UID efectivo debe ser distinto de `0`. La etapa final no debe enumerar SDK; debe contener los runtimes .NET y ASP.NET Core 10. Comprueba que ese usuario puede escribir en el directorio montado:

```powershell
docker compose exec -T api sh -c 'test -w /app/storage && echo T-06 > /app/storage/t06-verificacion.txt'
docker compose exec -T api cat /app/storage/t06-verificacion.txt
```

La lectura esperada es `T-06`. Este archivo es una marca de prueba; no contiene credenciales.

El volumen `upractice-storage` está montado en `/app/storage`. Esta comprobación acredita permisos y persistencia del montaje. En la base actual el registro de almacenamiento de archivos sigue pendiente; T-06 no implementa por sí mismo los endpoints ni la subida o descarga de CV.

## 6. Comprobar PostgreSQL efímero y persistencia de archivos

Este paso descarta los datos de la base de demostración de Compose, incluidos cambios de usuarios y contraseñas realizados durante la prueba. PostgreSQL utiliza `tmpfs`: su contenido no sobrevive a la detención del contenedor.

Conserva el ID del SuperAdmin obtenido antes y el archivo de verificación. Luego ejecuta:

```powershell
docker compose down
docker compose up -d --build --wait
docker compose ps
```

Comprueba:

1. Reconecta DBeaver a `5433` y repite la consulta del SuperAdmin: el seed reconstruido debe tener un ID nuevo. Las migraciones y los datos de demostración vuelven a cargarse.
2. Inicia sesión de nuevo usando las contraseñas iniciales de `.env`; los tokens anteriores deben reemplazarse.
3. Lee la marca del volumen:

   ```powershell
   docker compose exec -T api cat /app/storage/t06-verificacion.txt
   ```

   Debe seguir mostrando `T-06`: `down` conserva el volumen nombrado de archivos.

El contenedor manual `upractice-pg` y su volumen `upractice-pgdata` no forman parte de este Compose.

## 7. Detener la demostración

```powershell
docker compose down
```

Esto detiene la API y PostgreSQL de Compose; se pierde la base efímera y se conserva el volumen de archivos.

Para eliminar también el volumen de archivos de esta demostración, después de decidir descartar su contenido:

```powershell
docker compose down -v
```
